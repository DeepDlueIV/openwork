# Claude Code mods as OpenWork remote targets

Read-only feasibility research for the local remote-client prototype. This is **not an implemented integration** or a claim that a new Claude Desktop conversation can be created remotely.

## Supported surface

Claude Code mods run inside the native Claude Code process, including **Claude Desktop's Code tab**. This differs from a local MCP server, a separately spawned Claude Code CLI, Desktop Chat, and Cowork.

Minimum versions in the current documentation:

- Terminal Claude Code: 2.1.287.
- Desktop Code-tab bundled runtime: 2.1.286; check `/status` inside that surface, not the separately installed shell CLI.
- Desktop WSL sessions do not load plugins/mods.

Inspect the types generated by the actual installed version at `.claude-plugin/types/claude-code/index.d.ts` before writing the adapter. Public GitHub declarations can lag the documentation.

## Native operations

| OpenWork responsibility | Documented mods API | Qualification |
| --- | --- | --- |
| Identify the native session | `$.session.id()`, `cwd()`, `root()`, `model()`, `version()`, `surfaces()` | Recheck the enrolled session and resolved directory before remote effects. |
| Submit a prompt | `$.prompt.submit({ text })` | Targets the hosting native session. Resolves when its turn starts, not when the answer completes. Keep plugin attribution; do not impersonate a user. |
| Read transcript | `$.session.messages()` | Recent context projection, capped at 4,096 entries. Published projection has no native message IDs/timestamps. |
| Observe progress | `turn.start`, `turn.complete`, session/tool lifecycle hooks | Filter child-agent events; do not claim idle after reload without a trustworthy current state. |
| Guarded stop | `$.turn.abort({ turnId })` | Associate the remote message with the actual native turn. Never abort a newer/unrelated user turn. |
| Background polling | `$.clock.every(...)`, `$.http.fetch(...)` | Session scoped; timers stop when the module reloads. Not a global daemon while all sessions are closed. |
| Persist journal | `$.store.get/set/delete/keys` | Plugin JSON storage, 4 MiB total, not a credential vault or a documented transactional/fsynced store. |
| Peer communication | `$.session.send({ to: { sessionId }, text })` | Subject to peer controls. Not another session's user prompt, read permission, or stop authority. |
| Create a top-level Desktop session | **No documented native method** | `$.agent.spawn` creates a background subagent, not a new Desktop sidebar conversation. |

The honest initial scope is **explicitly attach to an existing Code-tab session, then send/read/observe/stop**. Do not fulfill `remote-session:create` by returning the current session's ID or spawning a detached CLI/subagent.

Our existing remote-session authorization resolves control from owner-scoped admitted commands. An attached existing-session pilot therefore needs an **explicit attach/admission contract**; possession of a native session ID alone is not authority. That change has not been made.

## Packaging and runtime restrictions

A mod consists of a plugin manifest, `hooks/hooks.json` with a `modules` declaration, and a hooks module exporting `register(on, options)`.

`register` receives the registrar/configuration, not `$`; the native API object arrives in event hooks. External operations must use statically spelled calls through `$`:

- No Node APIs, direct network/filesystem access, timer globals, dynamic imports, or `require`.
- Imports must be relative plugin-local files, apart from the supported `claude-code` module.
- Do not alias/destructure `$` namespaces or pass `$` into imported/nested functions.
- `$.http.fetch` returns `{ status, ok, headers, text }`, not a standard streamed `Response`.
- Native HTTP cancellation, redirect refusal, and timeout guarantees must be established from the installed API; do not assume Node fetch semantics.

`packages/remote-sessions` is consequently **not a drop-in import**. Its pure protocol/state-machine design can be reused, but its timer bounding and HTTP transport need a mods-compatible port. The current inventory engine discriminator only accepts OpenCode v1/v2; never label Claude as either.

## Safety requirements

- OpenWork sign-in and explicit per-session remote opt-in remain separate from native Anthropic sign-in.
- Never export native Anthropic credential handles or subscription credentials to OpenWork.
- Keep secrets out of plugin files, prompt/transcript text, journals and ordinary `$.store` JSON. Secure persistent login needs an explicitly installed credential helper or another reviewed auth flow.
- Preserve native permission decisions: observe permission/question hooks and return `next(e)` unchanged. No automatic approvals.
- Prompt submission has no documented durable caller message-ID deduplication. Use **at-most-once** send recovery and retain ambiguous receipts; text comparison is not deduplication.
- Start with idle-only admission. A queued prompt can outlive a remote timeout, and no queued-prompt cancellation handle is documented.
- `/clear`, `/resume`, and `/branch` can change native identity. Stop the old receiver and require fresh enrollment rather than carrying authority into a new session.
- Do not implement a cross-session lock using non-atomic `store.get` followed by `store.set`. Partition journals by account and native session and use one writer.
- Managed policies, hook trust, `allowManagedModsOnly`, `disableAllHooks`, network policy, and plugin marketplace restrictions continue to apply.

## Suggested validation

1. Validate/test the package without sign-in or live network using `claude plugin validate --strict` and `claude plugin test`.
2. Test enrollment, idle-only prompt submission, status, waiting, guarded stop, disable, identity changes, reload and ambiguous-send recovery with the installed build's mocks.
3. Prove one actual prompt/reply in a manually enrolled Desktop **Code-tab** conversation, including visible native approvals.
4. Establish a separate supported top-level creation mechanism before claiming full remote-session parity.
