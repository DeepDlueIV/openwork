The recommended Azure path is Helm on Azure Kubernetes Service with Azure Database for MySQL Flexible Server. Use the AKS application-routing add-on's managed NGINX Ingress controller for browser-facing HTTPS and host routing.

## What Azure manages

- AKS control plane, node pools, virtual networking, and managed identities
- the managed NGINX ingress entry point and public IP
- Azure Database for MySQL Flexible Server, encryption, backups, and failover
- Azure DNS and certificate storage when you use those services

The OpenWork chart manages Deployments, Services, ConfigMaps, Secret references, probes, the Ingress, and the database migration Job.

## Azure checklist

1. Confirm the subscription is enabled and register the required resource providers.
2. Check regional vCPU quota and MySQL Flexible Server availability before creating AKS.
3. Create AKS and MySQL in a VNet topology that permits private database traffic.
4. Store `DATABASE_URL`, `BETTER_AUTH_SECRET`, and `DEN_DB_ENCRYPTION_KEY` in a Kubernetes Secret.
5. Start from the chart's `values.azure-ingress.yaml` example.
6. Configure the ingress certificate, install the chart, and verify migrations and readiness.
7. Point both hostnames at the ingress address and confirm trusted HTTPS.

For exact Azure CLI commands, values, TLS options, migration troubleshooting, verification, and cleanup, follow the [Azure AKS operator runbook](https://github.com/different-ai/openwork/blob/dev/docs/azure-aks-helm.md).

## Azure Container Apps with Terraform

### What it deploys

The experimental module deploys Den API and web as HTTPS-only Container Apps, a singleton manual migration Job, MySQL Flexible Server 8.4 (or your existing database), managed Container Apps secrets with optional Key Vault references, and a new or existing environment and Log Analytics workspace. Application replicas do not run migrations. The native Job start is followed by a read-only observer of the exact execution; only `Succeeded` permits application rollout. Default image references and all overrides must be digest-pinned. The default API is 1 vCPU / 2 GiB and web is 0.5 vCPU / 1 GiB.

### Support level

<Warning>
  Experimental: pin a reviewed module commit. The Job starts through native AzAPI, but ARM acceptance is not container completion: terminal observation currently needs Python 3 and an authenticated Azure CLI on the Terraform runner. This read-only observer never starts or retries a Job. It is not a provider-native terminal waiter. Custom domains, private registries, Key Vault references and existing environments/databases have mocked rather than new live coverage.
</Warning>

Use Terraform or OpenTofu >= 1.11, < 2.0. You provide an existing resource group with resource creation, Job start and execution-read permissions; the default database deletion lock also needs management-lock write/delete permission. The module creates no role assignments. A subscription owner registers `Microsoft.App`, `Microsoft.DBforMySQL`, `Microsoft.Network` and `Microsoft.OperationalInsights` first. Default hosts have Microsoft-managed HTTPS certificates. Email is optional for setup/sign-in; invites and password reset require SMTP or Resend.

### Upgrade notes

When adopting this module from legacy per-replica migrations, use a maintenance window: freeze all deployment/retry/autoscale sources, stop and drain every old migration-capable revision and shared database consumer as needed, verify terminal containers and absence of old DB sessions/in-flight DDL, and fence old migration credentials. **Do not start the new Job if this exclusion cannot be established.** After its exact digest's execution succeeds, start API-only replicas and verify data and sign-in. Never reactivate legacy migration-capable definitions on rollback. Application migration locking and schema-compatibility manifests are separate work, not provided by this module.

Existing generated secret addresses and values are preserved; adoption must not rotate the auth secret or encryption key. Tag-only image overrides must be replaced with manifest digests. Existing database URLs must use `sslaccept=strict`; unverified TLS is rejected. For existing databases, `migration_database_url` accepts a separately provisioned DDL principal for the same host/port/schema as the app's `database_url`; only the Job receives it. Managed-database user provisioning remains a least-privilege follow-up. The Job does not receive app authentication or email secrets.

### State guidance

Use encrypted remote state with restricted access and locking, configured in your root module. For S3 state use `use_lockfile = true`, not DynamoDB. The MySQL administrator argument is write-only, but preserved random values and Container Apps app/Job secrets remain in state because those provider secret fields are not write-only. Losing the encryption key makes stored credentials unreadable. Existing Key Vault reference values remain outside state.

The default Azure `CanNotDelete` lock protects out-of-band database deletion; **Terraform destroy can remove its own lock**, so it is not a Terraform `prevent_destroy` guarantee. Separate production database state where needed. No lock file is shipped inside the reusable module; generate and keep a root lock for your chosen tool rather than assuming Terraform and OpenTofu registries have identical checksums.

### Cost notes

Earlier short one-replica runs were estimated below USD 1, not settled invoices; two replicas cost more. Use Azure pricing for your reservations, logs and traffic. Disposable tests explicitly disable deletion protection. Environment deletion took 25–28 minutes in prior runs, and Log Analytics needs permanent purge. Verify both active and soft-deleted inventories before removing local state/secrets.
